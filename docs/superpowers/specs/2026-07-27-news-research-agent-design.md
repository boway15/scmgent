# 无搜索 API 的跨境资讯研究 Agent 设计

## 1. 背景

现有跨境资讯模块依赖固定 RSS 与 RSSHub 路由。RSSHub 只能把已知页面转换为订阅，不能主动发现新来源、扩展搜索词或追踪原始出处；部分路由还存在空结果、404、503 和目标站限流。因此当前采集数量少、覆盖面窄，RSSHub 常驻容器的资源投入与业务价值不匹配。

本次改造不引入付费搜索 API，也不部署 OpenClaw。系统借鉴 OpenClaw 的“主动检索、打开网页、判断价值、保留出处”模式，在现有 scm-agent 内实现每天一次的自动研究任务。

## 2. 目标与约束

### 2.1 目标

- 广泛发现跨境电商、家具家居、平台运营、竞品、物流海关、政策合规、营销和 AI 资讯。
- 每天自动采集一次，同时保留页面手动补采能力。
- 候选资讯尽量完整入库，由人工标记“采用”或“忽略”；第一阶段不以候选数量为限制。
- 复用现有资讯表、去重、分类、任务日志和飞书同步能力。
- 移除 RSSHub 常驻服务及其配置依赖。

### 2.2 已确认约束

- 当前没有合适的搜索 API。
- 不新增常驻搜索服务。
- 不依赖宿主机任务计划。
- 生产调度继续使用现有 Compose `cron` 服务。
- 动态浏览器仅在任务执行期间启动，任务结束后退出。

### 2.3 不在本期范围

- 绕过登录、付费墙、验证码或目标站反爬机制。
- 自动发布全部候选资讯。
- 自动生成业务决策或执行建议。
- 自动训练模型；人工反馈仅作为后续规则优化的数据基础。

## 3. 方案选择

### 3.1 采用：查询型新闻订阅 + 官方站点监控 + 按需浏览器

系统使用三层发现渠道：

1. Google News、Bing News 等公开查询型 RSS，根据业务关键词矩阵动态生成检索 URL。
2. 官方公告页、Sitemap、原生 RSS/Atom 与行业站点列表页。
3. 对前两层发现但无法通过普通 HTTP 提取的动态页面，按需启动 Chromium 抽取正文。

此方案不依赖搜索 API，不增加常驻服务，并且能复用当前 Node/Hono 采集链路。

### 3.2 未采用：临时 SearXNG

SearXNG 可以聚合多个搜索引擎，但若从页面或现有 `cron` 自动启动临时容器，需要让应用获得 Docker 控制权限。挂载 Docker Socket 会扩大安全边界，且临时启动、健康检查和清理会增加故障点，因此本期不采用。

### 3.3 未采用：纯浏览器搜索

自动操作通用搜索结果页容易触发验证码，也容易因页面结构变化失效。浏览器只作为正文提取补充，不作为唯一发现入口。

## 4. 总体架构

```text
Compose cron（每天 08:00）
  → POST /api/tasks/news-ingest
  → 研究任务互斥与当日幂等检查
  → 根据策略生成查询矩阵
  → 并发受控地执行三类采集器
      ├─ 查询型新闻 RSS
      ├─ 官方站点 / Sitemap / 原生 RSS
      └─ 动态网页浏览器补抓
  → 标准化候选
  → URL、标题、正文去重
  → 基础垃圾过滤
  → 规则分类与可选 Dify 增强
  → 以 pending_review 写入本地候选池
  → 记录来源、查询词和任务日志

管理员页面
  → 查看候选
  → 标记已采用 / 已忽略
  → 已采用记录按需同步飞书
  → 手动补采 / 强制重跑
```

任务继续通过 HTTP 同步执行。现有 `run-task.sh` 的最长执行时间为 3600 秒，研究任务应设置更短的内部总预算，默认 30 分钟，确保超时前能完成资源清理并返回任务摘要。

## 5. 查询策略

### 5.1 查询矩阵

查询词不采用所有关键词的笛卡尔积，而是按模板生成，避免请求量失控：

- 区域：美国、英国、德国、法国、意大利、欧盟。
- 平台：Amazon、TikTok Shop、Wayfair、Walmart、Shopify。
- 品类：家具、沙发、升降桌、办公桌椅、人体工学、家居。
- 业务主题：平台政策、关税、海关、物流、海外仓、营销、广告、AI。
- 重点品牌：沿用 `openclaw-policy.json` 中的品牌及别名。

示例模板：

- `{平台} seller policy update {区域}`
- `{品类} market trend {区域}`
- `{品牌} news OR launch OR expansion`
- `{区域} tariff customs furniture`
- `跨境电商 {主题} 最新政策`

策略文件维护模板、语言、地区、启停状态、优先级和每次最大返回量。默认回看 7 天；同一查询连续多次无新增时降低频率，持续产生有效候选时提高优先级。

### 5.2 来源追溯

新闻聚合链接只用于发现。系统尽量解析并保存原始发布站点 URL；无法解析时保留聚合 URL并标记 `aggregator_only`，供人工识别。来源域名、发现渠道和命中的查询词必须随候选保存，确保可追溯。

## 6. 采集与处理

### 6.1 采集器边界

- `query-feed collector`：生成查询 URL，解析 RSS/Atom，并输出统一候选。
- `site collector`：读取 Sitemap、列表页或原生订阅，负责官方及固定高价值站点。
- `browser extractor`：仅接收已发现 URL，不负责无限探索；使用并发 1–2、页面超时和域名限速。

每个采集器统一返回标题、链接、发布时间、摘要、正文、来源域名、发现渠道、查询词和错误信息。

### 6.2 候选入库原则

- 第一阶段取消“低相关度直接丢弃”，相关度仅用于排序。
- 仅过滤确定的垃圾内容、无标题或无链接记录、超出回看窗口的旧闻。
- 新记录默认 `pending_review`。
- `published` 表示人工采用；`ignored` 表示人工忽略。
- 只有 `published` 默认进入飞书同步队列，避免候选噪声污染资讯总表。

### 6.3 去重

依次使用：

1. 去除追踪参数后的规范化 URL。
2. 标题归一化后的精确匹配。
3. 正文或摘要内容哈希。
4. 可选的标题相似度检查。

同一事件的多来源报道不强制全部合并；官方一手来源优先，其他来源可标记为关联报道。

### 6.4 浏览器生命周期

- Chromium 安装在 Web 镜像中，但不常驻运行。
- 仅在普通 HTTP 抽取失败且候选优先级达到阈值时启动。
- 每页独立超时，限制页面数量、并发数和总执行预算。
- 使用 `finally` 关闭页面、上下文和浏览器；任务异常退出也应执行清理。
- 验证码、登录页或访问拒绝直接记录失败，不尝试绕过。

## 7. 数据模型调整

复用 `news_sources`、`news_articles`、`news_ingest_logs` 和通用 `task_runs`，通过增量字段支持研究任务：

### 7.1 `news_sources`

- 扩展来源类型：`query_feed`、`sitemap`、`web_page`。
- `config_json` 保存查询模板、地区、语言、提取方式和浏览器策略。
- RSSHub 来源迁移为停用状态，不删除历史关联数据。

### 7.2 `news_articles`

建议增加：

- `discovery_channel`：`query_feed`、`official_site`、`native_feed`、`browser`。
- `discovery_query`：发现该资讯的查询词。
- `source_domain`：原始来源域名。
- `reviewed_at`、`reviewed_by`：人工审核记录。
- `aggregator_only`：是否未能解析到原始来源。

现有 `status` 已具备 `pending_review`、`published`、`ignored`、`archived`，无需新增审核状态枚举。

### 7.3 日志

任务摘要至少记录：

- 查询数、来源数、抓取数、新增数、重复数、垃圾过滤数。
- HTTP 抽取成功数、浏览器补抓数及失败数。
- 待审核数、人工采用数不在采集任务中计算。
- 每个查询或来源的耗时、错误类型和连续失败次数。

## 8. 调度与并发

- 保留每天 `08:00` 的现有 `/api/tasks/news-ingest` 路径和调度时间，接口内部切换到新的研究管线，避免部署配置迁移；页面名称改为“跨境资讯研究”。
- 非强制运行时维持“当天成功执行过则跳过”的现有幂等保护。
- 使用数据库任务锁或活动任务检查，禁止自动任务与手动任务并发执行。
- 手动“补充采集”遵守当天幂等；“强制重跑”跳过当日保护，但仍受互斥锁约束。

## 9. 页面调整

资讯页面默认展示候选审核队列：

- 筛选：待审核、已采用、已忽略；来源渠道、主题、国家、平台、品牌、日期。
- 排序：相关度、来源等级、发布时间、采集时间。
- 操作：采用、忽略、恢复待审核、打开原文。
- 状态区：最近自动任务、下次执行时间、查询成功率、浏览器补抓状态。
- 操作区：补充采集、强制重跑。

来源管理区隐藏或移除 RSSHub 配置，新增查询模板、官方站点和采集方式展示。

## 10. 错误处理与安全

- 单一查询、来源或页面失败不得中断整批任务。
- HTTP 请求使用超时、有限重试、指数退避和域名级并发限制。
- 对 403、429、验证码和登录页不重试或仅延迟一次，避免持续施压目标站。
- 禁止访问内网、回环地址和云元数据地址，防止将候选 URL 变成 SSRF 通道。
- 限制响应大小、正文长度、重定向次数和允许协议。
- 浏览器禁用文件下载，并使用独立临时目录。
- 任务结束返回部分成功摘要；只有任务初始化或数据库不可用时标记整批失败。

## 11. 测试与验收

### 11.1 自动测试

- 查询模板生成：覆盖不同地区、语言和主题，且不产生无界组合。
- 查询型 RSS 解析：RSS、Atom、缺失日期、聚合跳转链接。
- URL 安全校验：拒绝内网、非 HTTP 协议和异常重定向。
- 去重：追踪参数、标题重复、内容重复。
- 审核流转：`pending_review → published/ignored → pending_review`。
- 飞书同步：仅同步 `published`，不会自动同步全部候选。
- 任务幂等与互斥：同日跳过、强制重跑、并发拒绝。
- 浏览器资源清理：成功、超时和异常路径均关闭浏览器。

### 11.2 验收标准

- 连续 7 天每天自动执行一次，无需人工启动任务。
- RSSHub 容器停止后，资讯任务仍能独立运行。
- 每次任务可看到查询级和来源级统计及失败原因。
- 候选资讯均可追溯到来源域名、发现渠道和查询词。
- 低相关度候选不会被静默丢弃，可在待审核列表查看。
- 人工采用后才进入默认飞书同步流程。
- 单个来源失败不会导致整批任务失败。
- 任务完成或失败后不存在遗留 Chromium 进程。

## 12. 迁移顺序

1. 增加查询策略、采集器和候选审核所需字段。
2. 接入查询型新闻 RSS与官方站点，暂不启用浏览器。
3. 调整入库规则和页面审核流程。
4. 接入按需 Chromium 补抓并增加安全限制。
5. 连续观察 7 天覆盖率、重复率、失败率和人工采用率。
6. 达标后从 Compose 删除 RSSHub 服务、依赖和 `RSSHUB_BASE_URL`。
7. 将历史 RSSHub 来源停用，保留历史资讯和关联记录。

## 13. 后续评估指标

第一阶段不限制候选总量，但仍通过指标判断方案是否有效：

- 每日新增候选数。
- 不同主题、地区、平台和品牌的覆盖率。
- 原始来源解析成功率。
- 重复率和垃圾过滤率。
- 人工采用率。
- 每条采用资讯的平均抓取成本与任务耗时。

观察期后再根据人工采用率缩减低价值查询、提升高价值来源权重，并决定是否需要接入正式搜索 API。
