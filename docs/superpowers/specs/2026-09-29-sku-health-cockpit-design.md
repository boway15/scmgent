# SKU 健康灯筛选与整 SKU 供应舱

**版本**：v1.0（2026-09-29）  
**定位**：规划入口用「库存健康灯」巡检并可多选筛选；规划详情升级为整 SKU 供应舱，一眼看到头寸、分仓风险与供应链路。  
**本期做法**：两期交付。一期改入口列表与 overview API；二期强化现有 `SkuInventoryPlanningPage` 网络视图（方案 A），组合既有池/跟单/发运查询，不新开路由。  
**本期不做**：入口列表供应摘要列；舱内改目的仓/写分配；改健康计算公式；第三档「全部商品」以外的范围逻辑。

---

## 1. 目标

运营在「SKU 库存规划」应能：

1. 按库存深浅（超备 / 健康 / 风险 / 高风险 / 暂停）找到要对的 SKU，而不是看主数据补货策略灯。
2. 进入单个 SKU 后，在同一页完成「该不该补 → 各仓怎样 → 货在哪条链路上」的判断。

成功标准：

- 入口列展示健康灯（蓝/绿/黄/红/灰），文案对齐业务四档 + 灰档。
- 入口支持健康灯多选筛选，服务端分页正确。
- SKU 行灯色 = 各仓最新健康快照的**最差仓**聚合。
- 详情默认网络供应；含决策条、三池头寸、带健康灯的分仓一览、开放批次 / 未结跟单 / 发运只读列表、时间轴。
- 不改变 `skus.replenish_light`（补货策略灯）语义；库存总览补货灯列本期不动。

---

## 2. 决策

| 项 | 选择 |
|----|------|
| 入口展示 | 健康灯替换原「补货灯」列（策略灯改名避免误解） |
| SKU 聚合 | 最差仓优先：`红 > 黄 > 绿 > 蓝 > 灰`（与 `network-replenishment` 现网优先级一致） |
| 灰灯 | 单独一档；列表可显示；筛选芯片含「灰（暂停补货）」 |
| 筛选交互 | 多选芯片；不选 = 全部；例：红+黄 = 待处理池 |
| 无快照 | 显示「未评估」；本版不进筛选芯片 |
| 详情形态 | 强化现有规划详情（网络默认），不新开 `/inventory/sku/:id` |
| 供应链路数据 | 前端按 `skuCode` / `skuId` 组合调用既有 API；规划 API 仅补分仓健康灯字段 |
| 健康公式 | 不改；读 `inventory_health_snapshots` 最新仓行 |

## 3. 口径

### 3.1 健康灯业务含义

| 业务叫法 | 系统值 | 含义（决策灯） |
|----------|--------|----------------|
| 库存超备 | `blue` | 确定覆盖天数 > 超备阈值（默认 180），且无需补货 |
| 健康 | `green` | 交期内不断货、安全窗不破、未超备 |
| 风险 | `yellow` | 有建议量，或安全破位日落入「总交期 + 安全天数」窗口 |
| 高风险 | `red` | 确定断货日落在总交期内，或 `uncoverableByNewPo` |
| 暂停补货 | `gray` | 滞销 / 即将停售等生命周期或滞销规则 |

覆盖天数影子灯（`calcInventoryHealth`）仅作对照，入口与舱决策条以快照中的决策灯为准（与规划详情 `healthStatus` 同源任务写入）。

### 3.2 与「补货策略灯」的区别

| | 健康灯（本期入口） | 补货策略灯（主数据） |
|--|--|--|
| 字段 | 健康快照聚合 | `skus.replenish_light` |
| 默认 | 无快照 → 未评估 | DB 默认 `red` |
| 含义 | 库存深浅 | 允不允许自动补（红必补 / 黄联动 / 绿不补） |

### 3.3 最差仓聚合

对每个 SKU，取 `inventory_health_snapshots` 中各 `warehouse_code` **最新一条**（`computed_at DESC, id DESC`），再按优先级取最大：

```
red(5) > yellow(4) > green(3) > blue(2) > gray(1)
```

灰低于蓝：灰表示暂停而非「更紧急」；有红/黄时仍以红黄为准。仅当所有仓均为灰（或最差为灰）时行灯为灰。

逻辑仓（如 `OVERSEAS`、`IN-PRODUCTION`、`ALL`）是否参与聚合：与规划看板 `latest_health` 一致——**凡快照中出现的 warehouse_code 均参与**；若后续看板排除逻辑仓，入口同步排除。

## 4. 一期：入口健康灯 + 筛选

### 4.1 页面

`SkuPlanningEntryPage`（`/inventory/planning`）

- 列标题：`补货灯` → `健康灯`
- 组件：`InventoryHealthBadge`；无值显示「未评估」
- 筛选：蓝 / 绿 / 黄 / 红 / 灰 多选芯片；变更时重置到第 1 页
- 保留：搜索、商品范围、进入规划链接

### 4.2 API

扩展 `GET /api/inventory/overview`（入口已用 `view=replenish`）：

| 参数 | 说明 |
|------|------|
| `healthStatuses` | 逗号分隔，多选；合法值 `red,yellow,green,blue,gray`；非法值忽略 |

响应每行增加：

| 字段 | 类型 | 说明 |
|------|------|------|
| `healthStatus` | `InventoryHealth \| null` | SKU 最差仓灯；无快照为 `null` |

筛选：仅当 `healthStatuses` 非空时，限制 `healthStatus IN (...)`；`null`（未评估）不匹配任一色。

分页：`total` / `page` 在筛选后计算。

实现建议：在 overview 查询路径用 SQL CTE（对齐 `planning-dashboard.ts` 的 `latest_health` + SKU 级 `CASE` 最差灯），避免 N+1。

### 4.3 客户端

- `api.getInventoryOverview` 增加 `healthStatuses?: InventoryHealth[]`
- 入口页 state 驱动芯片与 queryKey

### 4.4 验收（一期）

- [ ] 入口列为人读健康灯，不再默认整表红策略灯
- [ ] 单选红只出最差灯为红的 SKU；红+黄为并集
- [ ] 无快照 SKU 显示未评估，且不被五色筛选命中
- [ ] 分页 total 与筛选一致
- [ ] 商品范围（不含配件）与健康筛选可叠加

## 5. 二期：整 SKU 供应舱

### 5.1 页面结构

强化 `SkuInventoryPlanningPage`；打开 SKU 时**默认 `scope=network`**（已有则保持）。

自上而下五块：

1. **决策条**  
   最差健康灯（网络）· 有效供给 · 覆盖天数 · 建议量/建议日 · 确定断货日 · 网络/分仓切换（已有控件收敛到此条）

2. **供应头寸**  
   既有三池 MetricCard：在产 / 调拨在途 / 海外未定仓 / 无可用日

3. **分仓一览（增强）**  
   现有：仓码、有效供给、最近到货、缺货日、下钻链接  
   新增：各仓 `healthStatus`（`InventoryHealthBadge`）

4. **供应链路（新增，只读）**  
   - 开放批次：`GET /inventory/pools`（或 batches 列表）按本 SKU `q` 过滤，展示池、仓、数量、可用日  
   - 未结采购跟单：`getPurchaseTracking({ q: skuCode })`  
   - 发运：`getShipments({ q: skuCode })`  
   每块标题旁链到全页（三池 / 采购跟单 / 发运），并带 SKU 查询参数（若全页支持）

5. **需求与时间轴**  
   交期拆解 + 网络/分仓时间轴（现有下移，口径不变）

分仓模式下：决策条与时间轴切到单仓；供应链路仍可按 SKU 展示（全网链路），或在批次表用当前仓过滤——**默认全网链路**，避免分仓时丢失未定仓批次。

### 5.2 API 增量（二期最小）

`GET /api/inventory/planning/:skuId` 网络响应中 `warehouses[]` 增加：

| 字段 | 类型 | 说明 |
|------|------|------|
| `healthStatus` | `InventoryHealth \| null` | 该仓最新健康快照 |

批次 / 跟单 / 发运**不**强制塞进 planning 大包，避免接口膨胀；前端并行请求即可。若跟单/发运的 `q` 为模糊匹配导致串 SKU，则改为精确 `skuId` 参数（优先复用已有精确过滤；没有再补小参数）。

### 5.3 验收（二期）

- [ ] 进入规划默认网络供应，决策条可见健康灯与建议量
- [ ] 分仓一览每行有健康灯，与健康快照该仓一致
- [ ] 同页可见该 SKU 开放批次、未结跟单、发运（无数据时空态文案）
- [ ] 不提供舱内写分配 / 改目的仓
- [ ] 配件 SKU 直达仍可用，并保留配件标记

## 7. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 健康快照滞后导致灯色过时 | 决策条/入口注明快照来自日常任务；链到规划看板或重算入口（若已有权限） |
| overview 加最差灯 SQL 变慢 | CTE + 现有 SKU 过滤先收窄；必要时只对当前页 SKU 二次聚合（优先一次 SQL） |
| 跟单/发运 `q` 模糊串货 | 验收时核对；必要时补 `skuId` 精确过滤 |
| 用户仍把健康灯当成策略灯 | 列名「健康灯」+ badge title 用业务四档文案 |
